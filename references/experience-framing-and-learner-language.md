# 情境框架与学习者语言

用于所有新课、重大体验改稿和页面审阅。内部设计需要精确状态与评价术语，学习者体验需要自然的对象、行动和回应；两者必须分层，不能把制作与验收语言直接搬到课程里。

按 `imagineering-for-learning.md` 同时检查体验承诺、环境信息、知识动作与结果。禁用通用场所外壳不等于必须改成事故现场；安静探索、创作、正常示范和抽象对象也可形成自然入口。学科方法有具体收益即可，不强称现实唯一解法。

## 先从学科对象产生体验

课程先回答“学习者正在面对什么真实对象、现象、文本、作品、关系或事件”，再决定地点、角色和载体。不得因为需要持续事务或记录，就默认创建“审核台、观察台、实验台、工作台、控制台、指挥中心、研究中心”等通用场所，也不得默认授予“审核员、观察员、分析员、调度员”等岗位。

这类框架只有在以下条件同时成立时才可使用：

1. 学习目标本身要求真实的审核、观察、实验、调度或专业操作。
2. 场所、岗位和权限来自教材、职业实践或已确认的教学情境，不是为了包装题目。
3. 去掉该框架会损失目标所需的判断、协作、工具或后果。
4. 角色、对象和反馈会贯穿主线，而不是换个名称后继续普通题库。

不满足时，直接使用内容原生入口。例如数学从一段可见运动、建筑尺寸变化或NPC眼前的问题进入；历史从地点、人物行动和史料进入；科学从正在发生的现象、样本或装置进入；语言从真实交流与作品进入。课程标题优先命名知识问题、事件、对象或学习结果，不命名通用容器。

交付前做“换课检验”：把学科名和专有名词替换后，若同一“某某台/中心+岗位+流程”仍可无损套到多数课程，说明情境过于通用，必须重写。

## 沉浸式课程的体验决策

新建网页课先按[工作范围](work-scope.md)选择video_led_web、spatial_native_web或hybrid_web。以下视频规则只用于视频主导部分；原生空间部分以同一对象、规则和学习证据推进，不强加视频：

- 视频承担主线事件、上下文、节奏和学习推进，不是装饰片头。
- 按目标选择人物或无角色连续性。参与者路线可用贯穿 NPC；宏观、纪实、系统或对象路线可由稳定系统、对象、事件、资料集或状态承接。
- 视点按已批准 perspective 执行，不默认第一人称。发生视点切换时，通过同一连续性锚点返回，并保留学习状态。
- 核心交互从当前视频帧中的对象、人物动作、系统/对象变化、声音线索或事件热区进入。全局只保留必要播放和无障碍控件。
- 分支策略显式声明为线性、局部后果回归、带回归分支或持续分支。只改一段反馈文案不算真实后果；持续分支需要目标和制作依据。

持续创作、纯规则仿真或自主探索若需要持续对象状态，可选择原生空间/混合路线；长篇阅读或协作也按真实知识动作选择载体，不要求先挂接视频。视频主导中的局部体验仍保留精确暂停、返回和恢复，不把其主线改成无对象的通用工作台。

## 交互载体按动作选择

除场景卡、3D、360°和 Three.js 外，可选择：

- 画面内直接指认、测量、拖放、配对和少量参数控制；
- 规则驱动的二维仿真、虚拟仪器和变量实验；
- 时间轴回放、预测后运行、过程对比；
- 地图、关系网、路径和因果链操作；
- 原文批注、证据连线、作品修订和结构化写作；
- 部件组装、步骤演练、空间剖切与状态切换；
- 角色对话选择、口语输入、声音辨识或节奏模仿；
- 其他能由当前场景对象自然触发、产生目标证据并精确返回的视频内交互。

不设媒体配额。先写知识动作与证据，再选最低复杂度且能完成该动作的载体。

环境细节用于建立对象用途、关系、时间痕迹或行动线索，不能只是围着题目铺满道具。当前必需的单位、条件、概念和操作入口必须清楚可读；不要以沉浸为由隐藏字幕、基础提示、来源或键盘焦点。后台实现不外显，但教学示范和真实操作说明可以明确存在。

## 内部语言与学习者语言分层

内部文档和机器状态可以使用：

`核查、验证、证据、形成性评价、待审、首答、修订、目标状态、完成条件、验收、恢复点`

学习者可见内容必须翻译为：

- **对象**：当前是谁、什么物件、哪段材料、哪个现象。
- **动作**：看、比较、标出、调节、拆开、组合、解释、回应、修改。
- **结果**：对象发生了什么、NPC如何回应、当前判断改变了什么。
- **下一步**：回到哪个人物或事件，继续完成什么自然行动。

示例：

| 内部术语或坏文案 | 学习者可见写法 |
|---|---|
| 待核查 | “林老师还没看到你的尺寸理由”或直接不显示状态 |
| 继续核查 | “把两条边代回图纸”／“回去告诉林老师” |
| 收集证据 | “在信中标出支持这句话的原文” |
| 目标状态：未完成 | “还差一步：说明为什么排除这个结果” |
| 进入3D模块 | “拿起模型，看看管道里面怎样连接” |
| 任务完成 | NPC或对象呈现事务结果，再自然进入下一事件 |

只有当“核查、审核、验证”等词本身属于学科概念或真实职业动作时才可自然使用，例如代码审查、质量检验或数学验算；即使如此，也不能把系统进度状态写成剧情台词。

## 审阅

逐项检查课程标题、场景名、NPC台词、字幕、按钮、反馈、进度和结课：

1. 是否出现可替换到任意课程的“台、中心、岗位、任务流程”。
2. 是否把内部评价、验收或记录术语直接展示给学习者。
3. 是否只用同义词替换后台词，而没有写对象、动作和后果。
4. NPC 是否持续回应学习者和对象状态，而不是朗读课程步骤。
5. 交互是否从当前场景进入，并被下一段视频实际承接。
6. 结课是否以故事事务、作品、解释或对象变化收束，而不是显示“全部核查完成”。
7. 全部可听文本是否按[可录制台词与口语审阅](spoken-language-and-review.md)整段复查；即使没有后台词，拟人套话、名词堆叠、空泛收尾和编造听者反应仍须修订。必要讲解、专业术语、真实操作步骤和有依据的纠错可以直接说。

未通过时先改标题、脚本和界面文案，再做视觉与媒体生产。结构校验不能代替这项内容审阅。
